# 变更提案：基础库现代化与接入治理

## 动机

当前项目已经具备“组件能编译、示例能运行”的基础能力，但仍停留在仓库内使用阶段，尚未达到成熟基础库的交付标准。

主要症状：

- 外部项目接入依赖手工指定头文件目录与平台产物路径
- 库未提供标准 `CMake package` 导出能力
- 公共 API 面混入私有实现细节
- 示例程序与库构建边界耦合过深
- 自动化测试、CI、发布闭环缺失

这会直接限制项目在其他仓库中的复用性、可维护性与可信度。

## 目标边界

本次变更聚焦于“把项目从仓库内可运行，升级为可分发、可接入、可演进的 Qt 基础库”。

目标包含：

1. 建立项目基线规范与演进路线图。
2. 明确库、核心样式能力、示例程序之间的架构边界。
3. 明确 `CMake` 侧标准接入方式、安装方式与导出方式。
4. 明确公共 API 收敛策略，减少私有实现泄漏。
5. 明确测试、CI、文档与发布的补齐顺序。

## 非目标

1. 本次不直接补完全部缺失组件。
2. 本次不承诺保持现有接入方式长期兼容。
3. 本次不处理旧版本二进制兼容。
4. 本次不处理 Android 端 UI 适配细节。

## 方案设计

## 一、分层重构方向

建议将当前仓库逻辑拆分为三个稳定层级：

### 1. Core 层

承载主题、样式、动画、基础交互能力，例如：

- `QtMaterialTheme`
- `QtMaterialStyle`
- ripple、overlay、state transition

该层职责是提供可复用机制，不暴露业务无关的组件实现细节。

### 2. Widgets 层

承载具体 Material 组件，例如：

- Button
- TextField
- Tabs
- Drawer
- Snackbar

该层依赖 Core 层，但不得要求调用方直接感知私有头或内部资源结构。

### 3. Examples 层

承载演示与手工回归验证能力。

该层只能消费已安装或已导出的公共 target，不允许反向读取构建目录中的平台产物路径。

## 二、对外接入模型

### 主推荐路径

采用标准 `CMake package` 分发，调用方使用：

```cmake
find_package(QtMaterialWidgets CONFIG REQUIRED)
target_link_libraries(my_app PRIVATE QtMaterialWidgets::Widgets)
```

### 次推荐路径

支持源码方式接入：

- `add_subdirectory`
- `FetchContent`

要求无论哪种接入方式，对外暴露的 target 名、include 语义、链接方式都保持一致。

### 非推荐路径

- 手工写 `target_include_directories`
- 手工写平台相关 `.lib/.so` 文件路径
- 直接依赖构建目录产物

这些方式只适合作为过渡，不应继续作为文档主路径。

## 三、公共 API 收敛

### 收敛原则

1. 公共头禁止 `#include` 私有 `_p.h`
2. 公共头禁止泄漏内部目录结构
3. 未完成或实验态组件不得默认暴露到稳定公共接口面
4. 公共命名必须修正拼写与语义问题

### 处理策略

- `qmetarial` 目录名视为高优命名债务
- `table/menu/steps` 等未收敛接口进行分类：
  - 完整实现后保留
  - 未成熟则转入实验区
  - 空壳接口则移除导出

## 四、构建与发布治理

### CMake 侧

必须补齐：

- `install(TARGETS ...)`
- `install(EXPORT ...)`
- `configure_package_config_file(...)`
- `write_basic_package_version_file(...)`
- `BUILD_INTERFACE` / `INSTALL_INTERFACE`
- 统一命名空间 target

### qmake 侧

若保留，则必须满足：

1. 有 CI 验证
2. 有最小接入样例
3. 行为与 `CMake` 主路径一致

否则将其降级为非主支持构建系统。

## 五、验证闭环

项目需要建立三类验证：

1. 构建验证
   - Windows / Linux
   - Qt5 / Qt6
2. 接入验证
   - `find_package`
   - `add_subdirectory`
3. 行为验证
   - `QTest` 控件行为测试
   - 最小示例启动测试

## 决策记录

## Decision 1

以 `CMake` 为主事实来源，优先建设标准包导出与现代接入方式。

原因：

- 当前 README 已明显偏向 `CMake`
- 外部项目接入主要痛点集中在 `CMake` 分发模型缺失

## Decision 2

优先治理“库分发与公共 API”，晚于组件扩容。

原因：

- 如果分发模型与 API 面不稳定，新增组件只会放大技术债

## Decision 3

示例程序降级为消费方，而不是构建耦合方。

原因：

- Demo 应证明库可用，而不是借由内部路径耦合掩盖库的分发缺陷

## 风险清单

### 风险 1：命名迁移影响现有调用方

- 影响：目录名、target 名、包名收敛后，旧接入方式会失效
- 结论：非阻断
- 策略：在方案中明确分阶段迁移与临时兼容窗口

### 风险 2：公共 API 缩面时暴露隐藏耦合

- 影响：示例程序与部分组件可能依赖私有结构
- 结论：非阻断
- 策略：通过“先导出、后收敛、再切换示例消费方式”的顺序降低风险

### 风险 3：qmake 维护成本偏高

- 影响：双构建系统会放大维护负担
- 结论：非阻断
- 策略：若验证闭环建立失败，则降级 qmake 支持级别

### 风险 4：部分组件实际完成度低于 README 宣称

- 影响：对外文档与 API 稳定性认知失真
- 结论：非阻断
- 策略：在任务中加入组件导出分级与文档校准
