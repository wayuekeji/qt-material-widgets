# 变更提案：项目优化分析文档

## 动机

当前项目已经完成部分 CMake 包导出治理，但仍存在公共接口、实现分层、示例消费、测试闭环、文档一致性等方面的演进空间。用户要求分析当前项目并将可优化点整理成文档保存，因此需要把分析行为纳入 OpenSpec 变更，确保结论来自项目代码与现有规范。

## 目标边界

1. 扫描当前仓库的构建系统、公共接口、实现层、示例层、文档与验证闭环。
2. 识别高价值优化点，按优先级、影响范围、实施路径与验证方式整理。
3. 将分析结果保存为仓库文档，作为后续重构与治理的输入。
4. 保持本次变更为文档型交付，不直接修改库代码。

## 非目标

1. 本次不实施具体代码重构。
2. 本次不删除、重命名公共头文件或构建目标。
3. 本次不承诺二进制兼容策略。
4. 本次不替代后续针对单项优化的详细 OpenSpec 变更。

## 方案设计

分析文档应以 `openspec/project.md` 和项目代码为唯一事实来源，覆盖以下维度：

1. 构建与分发：CMake/qmake、安装导出、包配置、目标命名、示例消费方式。
2. 公共接口：安装头、私有实现泄漏、命名一致性、实验态接口暴露。
3. 实现分层：Core、Widgets、Examples 的职责关系与依赖方向。
4. 资源与运行时：qrc、字体、图标、运行时复制逻辑。
5. 测试与 CI：本地验证、接入验证、行为测试与持续集成缺口。
6. 文档与治理：README、Docs、OpenSpec、未来 ADR/CONTEXT 补齐方向。

输出文档应避免泛泛而谈，每个优化点必须包含证据、风险、建议路径和验证方法。

## 决策记录

### Decision 1

本次输出保存到 `Docs/ArchitectureOptimizationReport.md`。

原因：

- `Docs/` 是当前仓库已有文档目录。
- 报告属于工程治理文档，不应混入 README。
- 后续可从该报告拆分出独立 OpenSpec 变更。

### Decision 2

本次不创建或修改代码层接口。

原因：

- 用户请求是分析与文档保存。
- 具体优化项需要逐项建 Spec 后实施，避免一次性扩大影响范围。

### Decision 3

优先使用 `CMake`、公共头、核心实现与示例层作为分析证据。

原因：

- `openspec/project.md` 已明确 `CMake` 为主事实来源。
- 仓库定位是 Qt Widgets 基础库，构建接入与公共接口是最高杠杆点。

## 风险清单

### 风险 1：分析结论与已有未归档变更重叠

- 影响：可能重复列出现有 roadmap 中已提出的问题。
- 结论：非阻断。
- 策略：报告中区分“已有治理已启动”和“仍待补齐”的事项。

### 风险 2：缺少 ADR 与 CONTEXT

- 影响：部分架构意图只能从代码与 OpenSpec 推断。
- 结论：非阻断。
- 策略：报告明确将 ADR/CONTEXT 建设列为治理优化项。

### 风险 3：未执行完整 Qt 构建

- 影响：部分验证只能基于静态扫描与文件存在性检查。
- 结论：非阻断。
- 策略：文档标注验证证据来源，并列出后续需要补齐的动态验证。
